## 一、总体印象

平台提供的是**定制化的 JupyterHub 形态**：网页即开发环境，终端、JupyterLab、code-server 三选一，
GPU 资源（本项目为 Radeon 8060S，共享 64GB 内存）通过 ROCm 暴露给 PyTorch。
最大优点是**开箱即用**——不需要自己装驱动、不需要处理 CUDA 版本地狱，
`torch.cuda.is_available()` 进去就是 True。

最大约束是**限时**（本项目可用的是 60 分钟量级实例），这直接塑造了本项目
"重活一次性、轻活可重复"的设计（见 `compute_plan.md` 第六节）。

## 二、上手过程中的实际摩擦点

### ① 依赖冲突是最大的风险，而不是 GPU

这是本项目最重要的经验。`sentence-transformers` 这类"看起来无害"的高层封装会声明
`torch>=1.11` 依赖；一旦 pip 判定平台镜像里的 ROCm 定制 torch 不满足，
就会把它换成 CUDA/CPU 轮子，`torch.cuda.is_available()` 立刻变 False ——
**而实例只剩几十分钟，几乎不可能从容恢复**。

应对（已固化进项目）：

- 手写 mean-pooling 编码器（约 20 行）替代 `sentence-transformers`
- 只用 `pip install --only-binary=:all:` 装 `faiss-cpu` / `pymupdf` 这类无 torch 依赖的包
- 装完立刻 `diff` 环境快照，确认 torch 版本未变
- 检索层做 numpy 兜底，即使 faiss 装不上 demo 也不挂

### ② 持久化目录必须先验证，否则模型重下

3.6 GB 的模型如果每次会话都重下，60 分钟窗口会直接废掉一半。
但"哪个目录关机不丢"并不总是显然的。做法是先花 5 分钟做一次探针实验：

```bash
echo test > ~/work/persist_test.txt   # 关实例 → 重开 → cat 看是否还在
```

确认后再把 `HF_HOME` 指过去。**这 5 分钟能省掉后面 10–20 分钟的下载时间。**

### ③ 共享内存 ≠ 独立显存

64 GB 是统一内存，CPU 与 GPU 共享。好处是能装下 1.5B 甚至 7B 模型；
坏处是系统占用、Jupyter kernel、KV cache 会互相挤压，
**不能按"独立显存"的直觉去估容量**。同时跑两个 Python 进程各自加载模型是常见踩坑点。

### ④ 中文 PDF 抽取需要额外处理

PyMuPDF 对中文双栏论文的抽取质量总体可用，但有两个高频问题：

- **字间空格**：`检 索 增 强 生 成` —— 不修复会污染嵌入向量（已在 `chunker.merge_cjk_spaces` 处理）
- **参考文献污染**：一篇论文末尾几十条引用会把大量无关标题塞进向量库，
  导致检索质量骤降（已在 `fulltext.split_sections` 按 `References` / `参考文献` 截断）

这两点不是平台的问题，而是"在云上做中文全文 RAG"必然遇到的工程细节。

## 三、对平台的两条建议（若被问及）

1. **镜像里预置 `certifi` 与 CA 证书路径**。部分精简环境会出现
   `CERTIFICATE_VERIFY_FAILED`，本项目在 `discovery.py` 里显式加载 certifi 才恢复正常校验。
2. **在实例页面显著标注"持久化目录"**。目前需要用户自行试错确认，
   而这个信息直接决定模型要不要重下，是新手最容易浪费半小时的地方。

## 四、小结

本项目的技术选择几乎全部由平台约束倒推而来：

| 平台约束 | 设计决策 |
|---|---|
| 限时实例 | 六步验收阶梯 + `--dry-run` 通道，任何一步失败都能定位 |
| torch 版本脆弱 | 不装 `sentence-transformers`，手写编码器；numpy 兜底 |
| 内存共享、带宽有限 | 选 1.5B 小模型而非 7B+；把解码带宽作为核心分析指标 |
| 中文语料 | 手写字间空格修复 + 参考文献裁剪 |
| 无法保证环境下一次还在 | 一切可重建：正文现场抓取、索引随时重建、注册表校验 sha1 |
